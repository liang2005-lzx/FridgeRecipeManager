## 一、项目概述

### 1.1 选题背景

家庭冰箱里的食材经常"买了忘记吃"，最后过期扔掉。市面上的菜谱 App 大多只解决"做什么菜"，不解决"我现在的食材怎么办"。本项目把两件事合到一个 App 里：

1. 管理冰箱库存，按保质期算临期风险，到期前主动通知；
2. 用现有食材反推能做的菜，优先消耗快过期的食材，减少浪费。

### 1.2 目标与范围

| 加分扩展 | 联网能力：云端菜谱同步 + AI 生成菜谱 |

### 2.3 典型用例

**用例 1：录入一盒牛奶**

用户点 FAB → 进入添加页 → 选择分类"蛋奶"、单位"盒"、数量 1 → 点击"7 天"快捷 Chip 自动填到期日 → 保存 → 返回列表，卡片显示"剩 7 天 / 新鲜"的绿色标签。

## 三、总体设计

### 3.1 架构分层

采用"单 Activity + 多 Fragment + MVVM + Repository"结构，自上而下四层：

```
┌──────────────────────────────────────────────┐
│ UI 层（7 个 Fragment + MainActivity）          │
│ ViewBinding 绑定视图，只做渲染与事件转发        │
├──────────────────────────────────────────────┤
│ ViewModel 层（9 个 AndroidViewModel）          │
│ StateFlow 持有 UiState，combine 聚合数据流      │
├──────────────────────────────────────────────┤
│ 领域层（ExpiryAnalyzer / RecipeRecommender）   │
│ 纯函数式业务规则，可单独单元测试                │
├──────────────────────────────────────────────┤
│ 数据层（FridgeRepository + Room + Remote）     │
│ 本地唯一入口，联网模块（OkHttp）作为可选数据源   │
└──────────────────────────────────────────────┘
```

设计要点：

- **UI 与数据解耦**：Fragment 不直接碰 DAO，只订阅 `StateFlow<XxxUiState>`；
- **数据唯一入口**：所有读写走 `FridgeRepository`，联网同步/AI 保存也复用它；
- **算法独立**：`ExpiryAnalyzer`、`RecipeRecommender` 不依赖 Android 框架，能在 JVM 上跑单测。

## 五、核心算法设计

### 5.1 临期分析（ExpiryAnalyzer）

**剩余天数**：先把"现在"和"到期时间"都归零到当天 0 点再算差值，避免"今天到期"被算成 0.9 天。

```
daysLeft = floor((startOfDay(expiresAt) - startOfDay(now)) / 86400000)
```

**四档状态**：

| 状态 | 条件 | 语义 |
| --- | --- | --- |
| EXPIRED | daysLeft < 0 | 已过期 |
| URGENT | 0 ≤ daysLeft ≤ 2 | 今明到期，最该处理 |
| SOON | 3 ≤ daysLeft ≤ 5 | 快到期 |
| FRESH | daysLeft > 5 | 新鲜 |

**风险分（0–100）**：按"剩余天数越少分越高"的线性映射，并对过期项截断到 100：

```
risk = clamp(100 - daysLeft × 12, 0, 100)   // 过期项直接记 100
```

12 这个系数让 0 天≈100 分、8 天≈4 分，正好把"一周内"作为关注窗口。

**排序**：先按状态优先级（过期 > 今明 > 快到期 > 新鲜），同状态内按剩余天数升序。

**统计（看板用）**：总数、四档计数、预计浪费率 `wasteRate = 过期数 × 100 / 总数`、按分类计数 `byCategory`。

### 5.2 菜谱推荐（RecipeRecommender）

**匹配规则**：名称先归一化（去空格、去括号内容、统一大小写），再做双向 `contains`，因此"番茄"能匹配"小番茄"，"鸡蛋"能匹配"土鸡蛋"。

**打分公式（满分约 95）**：

| 分项 | 公式 | 设计意图 |
| --- | --- | --- |
| 覆盖率 | `覆盖率 × 50` | 现有食材能覆盖的用料越多越推荐 |
| 临期消耗 | `临期用料数 × 20` | 优先吃掉快过期的东西，减少浪费 |
| 缺料惩罚 | `max(0, 15 − 8 × 缺料数)` | 缺 1 样扣 8 分，缺 2 样就归零，避免推荐"要现买菜"的菜 |
| 快手加分 | ≤15 分钟 +10；≤30 分钟 +6；其他 +3 | 工作日更实用 |

输出 `RecipeMatch`：菜谱、得分、能否直接做（没有必需缺料）、匹配理由文案、已匹配/缺失/过期用料三组清单。

**示例**：冰箱有番茄（临期 1 天）、鸡蛋；菜谱"番茄炒蛋"需番茄+鸡蛋+葱（可选）。
覆盖率 2/2 = 100% → 50 分；临期用料 1 → 20 分；缺料 0 → 15 分；耗时 10 分钟 → 10 分；合计 95 分，`canCook = true`，理由"用料齐全，还能用掉临期的番茄"。

### 5.3 为什么算"非纯 CRUD"

- 天数计算做了时区归零，处理了"同日不同时刻"的边界；
- 风险分与推荐分都是多因子加权，答辩可现场改参数演示排序变化；
- 两个算法都在 `AlgorithmTest` 里被断言覆盖，不依赖数据库即可验证。

## 七、联网功能实现

### 7.1 在线菜谱同步

```
点击「☁ 同步云端」
   → CloudRecipeViewModel.syncFromCloud()
   → RecipeSyncService.fetchRecipes()（IO 线程，OkHttp GET）
   → 校验：HTTP 状态码 / 响应非空 / JSON 可解析 / 至少 1 条有效菜谱
   → FridgeRepository.replaceAllRecipes()（清空 recipes 表后逐条写入，食材表不动）
   → Flow 推送，列表自动刷新
```

异常分三类给出不同文案：网络层（超时/断网）、HTTP 层（4xx/5xx 带状态码）、数据层（格式不对/为空）。任何一类失败都只把状态行改成"离线模式：原因"，按钮变成"重试同步"，本地菜谱继续可用。

### 7.2 AI 生成菜谱

```
点击「✨ AI 生成一道菜」
   → 取当前库存前 12 条拼成"番茄 3 个、鸡蛋 1 盒……"
   → AiRecipeService：POST https://api.deepseek.com/chat/completions
      system: 只输出 JSON，不要 Markdown
      user  : 只能用这些食材设计一道家常菜 + 给定 JSON 结构
   → 清洗 ```json 包裹 → Gson 解析 → 校验菜名与步骤非空
   → 弹窗预览（菜名/耗时/用料/步骤/贴士）→「保存到我的菜谱」写入 Room
```

**安全与降级**：
- Key 只存在 `local.properties`，Gradle 读取后以 `buildConfigField` 注入，源码与 Git 历史中无明文；
- Key 为空 → 提示"未配置 AI Key，请在 local.properties 填写后重新构建"；
- Key 失效（401）→ 提示"AI Key 无效"；
- 请求超时 60 秒，失败提示后可直接重试，不影响其它功能。

### 7.3 网络配置

| 配置 | 位置 | 默认值/说明 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | `local.properties` | 无默认，需自行填写 |
| `RECIPES_REMOTE_URL` | `local.properties`（可选覆盖） | 默认 `https://ghproxy.net/https://raw.githubusercontent.com/liang2005-lzx/FridgeRecipeManager/master/server/recipes.json` |
| 权限 | `AndroidManifest.xml` | `INTERNET` + `ACCESS_NETWORK_STATE` |

> 说明：开发机直连 `raw.githubusercontent.com` 的 TLS 握手失败，因此默认走 ghproxy 代理；换网络环境可在 `local.properties` 覆盖地址。

## 八、关键技术实现

### 8.1 协程 + ViewModel

- 每个页面一个 `AndroidViewModel`，状态用 `MutableStateFlow` 私有、`StateFlow` 对外暴露；
- 数据聚合用 `combine(库存流, 筛选条件, 只看能做开关, 重试计数)`，一处变更自动重算；
- 异常统一 `.catch { emit(XxxUiState.Error(...)) }`，并在 `combine` 结果后加 `as XxxUiState` 显式转型（编译期必须，否则 catch 分支会被推断成 Content 子类型）；
- 请求都跑在 `viewModelScope`，页面销毁自动取消。

### 8.2 过期提醒（WorkManager）

- `ReminderScheduler.schedule(hour, minute)`：算"距下一个设定时刻的毫秒数"作为 initialDelay，再排 1 天周期的 `PeriodicWorkRequest`，`ExistingPeriodicWorkPolicy.UPDATE`，unique name `expiry_daily_check`；
- `ExpiryReminderWorker`（`CoroutineWorker`）：查询库存 → 筛 `daysLeft ≤ 2` → 无数据返回 `Result.success()` 不发通知 → 有数据走 `NotificationHelper.showExpirySummary`；
- 通知渠道 `channel_expiry`（IMPORTANCE_DEFAULT），通知 id 1001，`BigTextStyle` 汇总前 5 条，PendingIntent 打开 MainActivity；
- Android 13+ 检查 `POST_NOTIFICATIONS`，未授权时只写日志，不抛异常。

### 8.3 权限与降级

| 权限 | 类型 | 申请时机 | 拒绝后的表现 |
| --- | --- | --- | --- |
| POST_NOTIFICATIONS | 运行时（13+） | 首次进入食材列表 | 顶部提示条"通知已关闭，点此开启"，设置页显示状态并可跳系统设置；提醒任务照常运行但不发通知 |

### 8.4 自定义 View（Canvas 柱状图）

`CategoryBarChartView` 继承 `View`，在 `onDraw` 中自行计算：左边距为分类标签区（约 86dp），右侧按最大值等比换算柱长，柱体用圆角矩形，右侧标数量文字。`setData()` 只更新数据并 `invalidate()`，不重建视图。这样可以完全不引入第三方图表库，答辩时能逐行解释绘制逻辑。

### 8.5 文件导出（P2）

- `DashboardExporter.exportCsv`：三段式 CSV（总体统计 / 分类分布 / 优先处理清单），开头写 UTF-8 BOM，保证 Excel 打开不乱码；
- `DashboardExporter.exportChart`：把图表 View 画进 `Bitmap`（`view.draw(canvas)`），再压缩成 PNG，不需要截图权限；
- 文件写到 `getExternalFilesDir("exports")`，用 `FileProvider`（authority `${applicationId}.fileprovider`，路径声明在 `res/xml/file_paths.xml`）生成 content URI，`ACTION_SEND` + `FLAG_GRANT_READ_URI_PERMISSION` 交给系统分享面板；
- 全程不需要 `WRITE_EXTERNAL_STORAGE`。

## 十一、存在的问题与改进方向

| 问题 | 现状 | 改进方向 |
| --- | --- | --- |
| 无真机验证 | 界面运行时行为未点按 | 借同学设备安装调试包，重点验证通知、权限弹窗、分享 |
| AI Key 失效 | 演示前需换新 Key | 答辩前在 DeepSeek 控制台新建 Key 并写入 `local.properties` |
| 云端菜谱依赖代理 | 直连 GitHub raw 在本机不通 | 换网络或把 `server/recipes.json` 推到仓库后使用 ghproxy 地址 |
| 菜谱不能手动新建 | 仅内置/同步/AI 三种来源 | 增加"新建菜谱"页，复用 `addRecipe` |
| 菜谱库无分页 | 全量 Flow 加载 | 数据量大时改用 Paging 3 |
| 单机型适配 | 仅按约束布局设计 | 增加 `layout-sw600dp` 与大字体适配 |
| 提醒精度 | 周期任务受省电策略影响 | 换 `AlarmManager.setExactAndAllowWhileIdle` 或精确闹钟权限 |
